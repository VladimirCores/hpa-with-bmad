- (decision) Project scope: Enterprise GitOps Platform for offline-first, bare-metal multi-cluster Kubernetes deployment with IoT telemetry processing at 50k+ RPS. Source docs: 13 SP/UP files in docs/
- (assumption) Stack: Talos Linux, Cilium, Rook-Ceph, Argo CD, Kargo, Backstage, VictoriaMetrics, Pulsar, ClickHouse, Hasura, Infisical. Derived from docs/, confirmed by user brief.
- (decision) PRD audience: technical/dev teams (platform engineers, dev teams deploying via Backstage) AND business stakeholders (need platform metrics dashboards — alert throughput, device coverage, SLA compliance, cost per cluster).
- (decision) v1 MVP scope: POC on local dev machine with all components running. Focus on telemetry ingestion + processing pipeline. Bidirectional device communication deferred. CRM/WMS/ERP secondary — core responsibility is alert reaction + telemetry + device state. Billing external. Alert signals come from API (external directed stream for parallel processing).
- (decision) Alert detection: signals arrive via API as directed streams for parallel processing. Detection can be human-in-the-loop or AI agent. Every process has its own workflow (alert workflows are next step after v1). Core reaction: send signal to IoT devices, send signal to external hooks, provide realtime telemetry data with device state, record alert state through workflow.
- (decision) Production scale: millions of RPS per region, multiple clusters per region. Regional data sovereignty with central hub SPA for cross-region visibility. Central hub consumes API, CouchDB, and metrics connectors.
- (decision) Device communication: dedicated microservice, separate from core platform. Workflow engines: multiple — KNative + Restate for business processes, BPMN engine (Camunda considered) for structured workflows including reports (major part of alerting), separate billing workflow. Not core platform responsibility.
- (decision) Feature group updates: 4.3 Alert Signal Management also utilizes KeyDB (fast state tracking). 4.4 CouchDB in clustered mode, all data storages use Ceph persisted storage. New feature 4.9: Security — AuthN/AuthZ via Envoy Gateway (Casbin + Casdoor), dedicated PostgreSQL for users/permissions.
- (decision) KNative + Restate is the business logic layer — reacts to CouchDB changes, called from other system parts. Included in Alert Signal Management and Device State & Asset Tracking. Envoy Gateway split into separate feature (API Gateway — ingestion edge, API providing, OpenAPI spec). OpenAPI Specification required for internal and external use.
- (decision) AI agent engine extracted into separate feature block. Previously embedded in Alert Signal Management (4.3) — now standalone.
- (decision) AI Agent Engine scope: broader than LLMs — includes MCP (Model Context Protocol), A2A (Agent-to-Agent communication), and other AI/ML services. Not just alert response — full agent orchestration layer.
- (event) Reviewed with-gsd/ project structure. Existing implementation covers provisioning, Kargo/ArgoCD pipeline, Backstage, Knative, Spin apps, Casbin auth, Infisical, OpenAPI spec. PRD must distinguish built vs to-be-built. OpenAPI specs are Swagger YAML in Git (governance concern).
- (decision) Build from scratch — clean-sheet design. PRD describes full platform holistically, does NOT reference with-gsd/ as foundation. New solution.
- (decision) Multi-role system: manager, operator, administrator, technic, developer, CEO, client, and more. Each role has own human-in-the-loop functionality. Entity hierarchy: Companies → Clients → Assets (drones, vehicles, phones, wearable devices, IoT devices). CouchDB is central document store for ALL entity types — not just devices. §4.4 renamed to Entity & Resource Management.
- (decision) YugabyteDB used for system internal resources alongside CouchDB. KNative and Spin functions must have access to both CouchDB and YugabyteDB. Both are primary data stores, not just CouchDB.
- (decision) AuthZ via Casbin following Google Zanzibar specification — relationship-based access control (ReBAC), not simple RBAC. Roles derived from relationships between objects and users. Flexible, configurable model.
- (decision) Security implements three access control models: RBAC (base roles), ReBAC (Google Zanzibar via Casbin for relationship-based), and ABAC (Attribute-Based Access Control for attribute-based policies). Not just one model — comprehensive combination.
